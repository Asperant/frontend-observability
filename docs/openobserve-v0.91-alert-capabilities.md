| Notification body token substitution | SUPPORTED_WITH_LIMITATION       | Found only by live-firing a real scheduled SQL alert end to end (not by API round-trip alone — capability CRUD rows above only prove the template/alert are accepted and stored, not what actually renders). This stage's first template used `{alert_context_attributes.<key>}` and `{alert_status}` — both this repo's own invention, never OpenObserve's — and a real fire sent them to the destination as **literal, un-substituted text**. Extracting the pinned binary's own embedded UI help-copy strings gave the real, complete token set for a scheduled SQL alert: `{org_name}`, `{stream_type}`, `{stream_name}`, `{alert_name}`, `{alert_type}`, `{alert_period}`, `{alert_operator}`, `{alert_threshold}`, `{alert_count}`, `{alert_start_time}`, `{alert_end_time}`, `{alert_url}`, `{alert_trigger_time}` (+ `_millis`/`_seconds`/`_str`), `{alert_description}`. `{alert_agg_value}` is listed in the same UI help text but does **not** substitute for a `query_condition.type: "sql"` alert (live-confirmed twice) — the binary's frontend bundle shows it is only ever computed client-side, for the alert-builder form's own preview chart, never sent by the backend notification pipeline. There is therefore no real token exposing an SQL alert's actual matched/measured value at all on this pinned build. `{alert_threshold}`/`{alert_operator}` also can't stand in for a policy's real business threshold/direction: they reflect the alert's own fixed row-count trigger condition (this stage always uses `>= 1`), not the business threshold baked into the SQL's `WHERE` clause. **Separately, substitution does not JSON-escape the value it inserts**: a raw newline embedded in `{alert_description}` (this repo's own multi-line description, before the fix) produced a byte stream that failed `JSON.parse` on the receiving end — the entire notification silently arrived as an empty object, with no error surfaced anywhere in OpenObserve's own logs or UI. Fix: keep every custom per-alert value (severity, service/environment/version scope, business threshold, sample size, dashboard/runbook refs, dedup key) folded into one single-line `description` string (still using the one real `{alert_description}` token), never introduce a raw newline into a value destined for a JSON-shaped template body. `context_attributes` remains a real, accepted alert field (visible in OpenObserve's own alert-detail UI) — it is just never substitutable into a notification body via any `{...}` token on this pinned build.                                                                                                                                                                                                          |

| Alert history                        | SUPPORTED_AND_VERIFIED          | Corrects two earlier entries in this same row's history. First pass: SUPPORTED_AND_VERIFIED based only on a shape check (`{total,from,size,hits}` present), never a real fire producing a real hit. Second pass, after a live-fired real breach produced a genuine notification (scheduler logs: `Alert conditions satisfied` → `Alert notification sent`, real payload at alert-sink) but `GET /api/v2/default/alerts/history` still returned `{"total":0,"hits":[]}`: concluded NOT_SUPPORTED_ON_PINNED_BUILD, backed by grepping every DB migration name in the binary and finding no alert-history-equivalent table. That conclusion was wrong — the table search was the right method but an incomplete one, because the real backing store isn't a migrated SQL table at all: it's an internal **stream** (`triggers`, normally under the `_meta` org) that OpenObserve's own usage self-reporting subsystem writes to, and self-reporting ships **off by default** (`ZO_USAGE_REPORTING_ENABLED=false`). Setting `ZO_USAGE_REPORTING_ENABLED=true` plus `ZO_USAGE_REPORT_TO_OWN_ORG=true` (a real, confirmed flag on this exact pinned binary — `strings /openobserve \| grep ZO_USAGE_REPORT_TO_OWN_ORG` finds it) makes OpenObserve additionally copy each evaluation event into the _org's own_ `triggers` stream, which is what `/alerts/history` actually reads. Live-verified end to end after adding both flags (plus `ZO_USAGE_PUBLISH_INTERVAL=15` to shorten the default 600s flush interval for lab feedback speed) to `infrastructure/docker/compose.yaml` and recreating the `openobserve` container: a real fire now produces a real history row — `{"status":"completed","error":null,"retries":0,"evaluation_took_in_secs":0.0102,"query_took":9}` — matching the exact timestamp of the real notification received at alert-sink. No OpenObserve version upgrade needed; this was a missing-config gap in the lab's own compose file, not a build limitation. One caveat found along the way, unrelated to this fix: recreating the `openobserve` container without also recreating `alert-sink` breaks alert-sink's notifications (it uses `network_mode: "service:openobserve"`, a shared network namespace tied to that specific container instance) — any manual `docker compose up --no-deps openobserve` must be followed by the same for `alert-sink`, or notifications fail with a plain connection error until it's redone. `scripts/lab/alerts-history-shim.mjs` (the Logs Explorer workaround built while this was still believed unfixable) is no longer necessary for seeing alert evaluations, but is left in place since it is still a reasonable substitute for anyone running against a build/config where usage self-reporting isn't enabled. |
| Scheduler registration on enable     | NOT_SAFELY_VERIFIED             | Live-observed, not yet root-caused: a freshly-created, freshly-enabled alert was sometimes never picked up by the background scheduler loop at all (absent from `[SCHEDULER ...]` log lines for 7+ minutes while five sibling alerts, created and enabled identically, were evaluated every ~1 minute as configured) — the OpenObserve UI's own "Alert History" panel showed "No evaluation history available" the whole time, consistent with the scheduler simply never having registered it. Toggling the alert off then back on (`enabled:false` then `enabled:true` via a full-body `PUT`) reliably unstuck it within one evaluation cycle. Not yet determined whether this is a race in this pinned build's scheduler registration on create, or specific to this lab's setup — flagged here rather than silently worked around, since the practical effect is: if a newly-enabled alert never fires despite real breaching data, try disabling and re-enabling it before assuming the query/threshold is wrong.
