# OpenObserve v0.91.0 Stream/Schema/Lifecycle Capability Audit (Stage 15)

Every result below was verified against the real, pinned `public.ecr.aws/zinclabs/openobserve:v0.91.0`
container (`infrastructure/docker/openobserve/Dockerfile`), running inside this repo's own lab
(`pnpm lab:up`), reached only through its loopback-only admin port `http://127.0.0.1:5080` with the
lab's own root Basic Auth credentials — never through the public reverse proxy, never with a
private/undocumented API, and never by reading OpenObserve's source. Confirmed server identity:

```json
{
  "version": "v0.91.0",
  "build_type": "opensource",
  "commit_hash": "6c610514b4e0d017fb32b798f78d66526f79eb10"
}
```

(`GET /config`, unauthenticated — OpenObserve's own public build-info endpoint; blocked at the
reverse proxy, see [Management-plane isolation](#management-plane-isolation) below.)

Where the live behavior of the pinned binary was ambiguous or its exact accepted request shape
could not be established safely (without private-API/source access), the result is marked
`NOT_SAFELY_VERIFIED` rather than guessed. Nothing here is copied from OpenObserve's current web
documentation — every claim was reproduced against the running container in this session.

Reading the schema list alone would never reveal this asymmetry; only inspecting a real ingested record (or the raw wire payload) does. |

The lab manifests therefore treat `store_original_data: false` as a hard requirement, not merely a default, and Stage 15's drift classifier treats any drift to `true` on a canonical stream as `SECURITY_DRIFT`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## Management-plane isolation

Every one of the endpoints above was probed over `http://127.0.0.1:5080` — OpenObserve's own
loopback-only-published admin port, reached directly, never through the public reverse proxy. The
same probes repeated over the browser-facing `https://localhost:8443` (with the same admin Basic
Auth header, to isolate "is this path reachable at all" from "would auth succeed") all failed
before ever reaching OpenObserve:

| Path (via `:8443`)                               | Result |
| ------------------------------------------------ | ------ |
| `/api/default/streams`                           | `403`  |
| `/config`                                        | `404`  |
| `/api/default/streams/{stream}/schema?type=logs` | `403`  |
| `/api/default/rumtoken`                          | `403`  |
| `/api/default/_search?type=logs`                 | `403`  |
| `/api/organizations`                             | `403`  |

This matches the Stage 12 reverse-proxy configuration already in the repo
(`infrastructure/docker/reverse-proxy/conf.d/ingestion.conf`'s `location ~ ^/(_search|search|streams|users|organizations|dashboards|alerts|functions|pipelines|rumtoken|source-map|replay)(/|$)` and
`app.conf`'s `^/(web|config|es|aws|gcp|otlp|prometheus|cloud|license|node)(/|$)` denials) — Stage 15
adds no new browser-facing surface and relies on this existing, already-verified isolation; see
[`docs/openobserve-stream-schema-lifecycle.md`](openobserve-stream-schema-lifecycle.md#management-plane-isolation)
for the Stage 15-specific regression test that re-confirms this on every `test:stage15:streams` run.

## Methodology notes

- All destructive/write probing above (settings mutation, deletion) was done exclusively against
  disposable streams named `_chicek_lifecycle_test_*`, created for this audit and deleted at the
  end of the session. `_rumdata`/`_rumlog` were only ever read from during this audit.
- No OpenObserve source code was read; no undocumented/internal header or query parameter was
  used. All requests use the same root Basic Auth the rest of this repo's lab tooling already uses
  (`scripts/lab/provision-sanitization.mjs`, `scripts/lab/fetch-rum-token.mjs`).
- Every `SUPPORTED_AND_VERIFIED`/`SUPPORTED_WITH_LIMITATION` row above has a corresponding
  automated regression in `pnpm test:stage15:streams`
  (`scripts/lab/verify-stage15-streams.mjs`) so this audit cannot silently drift from the pinned
  binary's real behavior over time.
